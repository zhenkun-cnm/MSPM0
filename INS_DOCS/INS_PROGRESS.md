# 小车惯导进度

## 现在做到哪一步？

已开始第一版惯导实现。第一版不是自动导航，而是先让小车持续输出自己的二维位姿：

- `x`：从开机原点开始，前后方向累计位置，单位米。
- `y`：从开机原点开始，左右方向累计位置，单位米。
- `yaw`：开机后相对角度，单位度。
- `v`：当前线速度。
- `w`：当前角速度。

## 当前已知参数是什么？

| 项目 | 数值 | 说明 |
|---|---:|---|
| 左轮编码器 | M1 | 前进为正 |
| 右轮编码器 | M2 | 前进为正 |
| M1 标定 | 1054 counts/rev | 左轮一圈的实测标尺 |
| M2 标定 | 985 counts/rev | 右轮一圈的实测标尺 |
| 轮径 | 48 mm | 轮周长约 0.1508 m |
| 轮距 | 125 mm | 左右轮中心距 |

## 为什么不直接用加速度算位置？

因为小车上的 MEMS 加速度计会有零偏和噪声。加速度要积分两次才得到位置，误差会很快变大。第一版高精度室内小车定位，位置主要用轮子走过的距离，IMU 主要提供方向。

## 这次代码会输出什么？

串口会周期输出类似：

```text
[INS] X:+0.123 Y:+0.004 YAW:+1.20 V:+0.100 W:+0.50 L:+0.124 R:+0.122 SRC:M F:7
```

## 下一步要测什么？

1. 静止 10 秒，观察 `X/Y/V` 是否接近 0。
2. 向前推 1 米，观察 `X` 是否接近 1.000，`Y` 是否接近 0。
3. 原地左转 90 度，观察 `YAW` 是否接近 +90 或 -90。
4. 如果 yaw 正负方向不符合小车坐标系，只改 `INS_IMU_YAW_SIGN`，不改姿态角算法。

## 目前风险

- `app_imu_start()` 原来处于注释状态，INS 使用 yaw 前必须启动 IMU 任务。
- Flash、TFT、W25Q64 共用 SPI，总线互斥以后还需要继续整理。
- 第一版 Flash 日志是调试用途，不是最终黑匣子格式。

## 2026-07-14 本次实现进度

### 问：代码现在实现到了哪里？
答：第一版 INS 代码已经接入工程。新增 `app_ins` 任务，按 10ms 周期消费左右轮编码器增量，并读取最新 IMU yaw，输出 `x_m / y_m / yaw_deg / v_mps / w_dps`。

### 问：编码器数据怎么流到惯导？
答：`motor_encoder_task` 现在每 10ms 生成一帧 `MotorOdomDelta_t`，通过 `g_motorOdomQueue` 发给 `ins_task`。M1 按左轮、M2 按右轮处理，前进方向默认都是正。

### 问：Flash 做了什么调整？
答：保留 Flash JEDEC 检测，但取消上电擦写 `0x00000000` 的旧测试。INS 日志从 `0x00100000` 开始，避免破坏测试区和未来参数区。

### 问：下一步是什么？
答：Keil rebuild 已通过：`0 Error(s), 1 Warning(s)`。下一步上车做静止、直线 1m、原地 90 度、矩形路线四组测试，并根据串口输出修正 yaw 正负号和轮距/轮径标定。

### 问：这次还修了什么隐藏问题？
答：TFT 的 IMU 检查页面原来用 `xQueueReceive` 取走 IMU 数据，可能导致 INS 读不到最新 yaw。现在改为 `xQueuePeek`，TFT 只看最新姿态，不再消费队列。

### 问：为什么串口只看到 `[ATT]`，没有 `[INS]`？
答：`[ATT]` 是 IMU 姿态角日志，只能说明 yaw/roll/pitch 在运行，不能用来判断小车位置误差。`[INS]` 才是惯导位姿日志。若只看到 `[ATT]`，最可能是 `ins_task` 没有创建成功或烧录的不是最新固件。已做修正：

1. `IMU_PRINT_PERIOD_MS` 从 100ms 改为 1000ms，避免 `[ATT]` 刷屏。
2. `ins_task` 创建失败会打印 `[ERR] [INIT] INS task create failed!`。
3. INS 任务栈从 768 words 调整为 512 words，降低 FreeRTOS 16KB heap 压力。
4. 里程计队列从 32 帧调整为 16 帧，继续降低 heap 占用。

重新烧录后，正常应看到 `[INS] X:... Y:... YAW:... V:...`，这是判断 1m/2m/转 90 度误差的主日志。

### 问：INS 是否应该等 IMU 初始化完成后再打印？
答：是，已经修改。现在 `ins_task` 创建后不会立刻输出 `X/Y/YAW` 位姿日志，而是先等待 `g_imuDataQueue` 中出现第一帧 IMU yaw。等待期间每 1 秒最多打印一次：

```text
[INFO] [INS] Waiting for IMU yaw before pose output
```

拿到第一帧 yaw 后，INS 会把这一帧作为 yaw 零点，清空位姿和日志累计量，然后打印：

```text
[INFO] [INS] Ready: yaw zero=... src=...
```

从这之后才开始输出：

```text
[INS] X:... Y:... YAW:... V:... W:...
```

等待 IMU ready 期间，编码器队列里的早期脉冲会被丢弃，避免陀螺仪校准时不小心碰车导致起点被污染。Flash 日志也改为 INS ready 后再延后约 2 秒启动。

## 2026-07-14 手推测试后的阶段判断

### 问：当前手推测试结果说明什么？
答：第一版 INS 已经可以继续往下推进，但还不建议直接进入自动导航。当前结果：

- 约 100cm 直线，误差约 5cm。考虑手推和长度本身不标准，可以接受。
- 约 60cm 正方形回原点，X 误差约 2cm 到 8cm，Y 误差约 0.5cm 到 2cm，偏航角几乎无误差，表现很好。
- 当前主要问题不是算法明显错误，而是测试条件还不够标准。

### 问：下一步是继续测试还是进入下一阶段？
答：先做一轮标准化确认测试。通过后再进入下一阶段。标准测试计划已写入：

- `INS_DOCS/INS_STANDARD_TEST_PLAN.md`
- `INS_DOCS/INS_TEST_RECORD.md`

### 问：标准化测试怎么做？
答：

1. 1m 直线，重复 3 次。
2. 2m 直线，重复 3 次。
3. 60cm 正方形回原点，重复 3 次。
4. 原地右转 90 度，重复 3 次。
5. 每次结束停 2 秒，只记录最后 3 行 `[INS]`。

### 问：怎么判断是否通过？
答：

- 1m 直线：X 误差小于 5cm，Y 偏移小于 3cm。
- 2m 直线：X 误差小于 10cm，Y 偏移小于 6cm。
- 60cm 正方形回原点：最终 X/Y 误差均小于 8cm。
- 原地右转 90 度：Yaw 在 -90° ± 8° 内。

### 问：通过后做什么？
答：进入下一阶段：惯导复位/校准命令、更清晰串口测试菜单、Flash 日志读取方案。

### 问：当前测试算精准测试吗？
答：不算。当前阶段明确按“非精准确认测试”执行。原因是现在的条件仍然是手推、场地和尺量不够严格，路径也可能存在人工误差。因此当前测试只用于确认 INS 是否大体可用、方向是否正确、误差是否大致可接受。

### 问：当前测试能不能直接拿来改轮径、轮距或 counts/rev？
答：不能。当前非精准测试通过，只说明可以继续推进下一阶段准备；不直接用于最终标定，也不直接修改 `INS_WHEEL_DIAMETER_M`、`INS_WHEEL_BASE_M`、`MOTOR1_COUNTS_PER_OUTPUT_REV_CAL` 或 `MOTOR2_COUNTS_PER_OUTPUT_REV_CAL`。

### 问：什么时候才进入精准测试？
答：只有用户明确说“开始精准测试”时，才切换到精准测试流程。精准测试需要更严格的场地、测距、路径控制和重复记录。
