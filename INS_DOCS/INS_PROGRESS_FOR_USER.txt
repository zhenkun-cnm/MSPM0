答：主要看这行：

X/Y 是位置，YAW 是方向，V 是速度，W 是角速度，L/R 是左右轮累计距离。

答：

3. 输入 ins reset。
4. 如果要保存日志，输入 ins log on。
5. 开始推车或跑车。

问：Flash 存什么？
答：存 INS 位姿日志，不存完整原始 IMU 波形。每条记录包括开机后毫秒时间戳、X/Y、Yaw、速度、角速度、左右轮增量、yaw 来源。

问：这个时间戳是什么意思？
答：时间戳叫 boot_ms，意思是“小车从开机运行到这条日志时经过了多少毫秒”。它不是年月日时分秒，因为当前没有接入 RTC 实时时钟，也没有上位机校时。

问：什么时候存 Flash？
答：默认不存。只有你输入 ins log on 后才开始存，每 200ms 存一条。输入 ins log off 后停止。

问：Flash 里存了但我怎么看？
答：输入：

它会把 Flash 里的 INS 日志从串口打印出来，每行以 [INS_LOG] 开头。如果没有记录，会显示 [INS_LOG] empty。

打印出来的 boot_ms 会随着日志递增，正常情况下每条大约增加 200ms。

2026-07-17 - 修复 nav square 只走一条直线

这次修了什么？
答：`nav square 0.6` 不再按理想正方形四个顶点计算，而是改成明确动作序列：
前进 0.6m -> 左转 90度 -> 前进 0.6m -> 左转 90度 -> 前进 0.6m -> 左转 90度 -> 前进 0.6m -> 左转 90度。

为什么要这样改？
答：你的小车是后轮双电机、前轮万向轮，而且转向要求是单轮定轴转向。单轮转向时车的 X/Y 会变化，所以不能假设“转向只改变 yaw”。如果继续用理想顶点，会导致导航层对位置判断不符合真实车体运动。

为什么之前可能只走一条直线？
答：nav 和 motion 之间没有明确的命令回执。旧逻辑只看 motion 是否为 IDLE，可能把“转向命令没有真正启动”误判成“转向已经完成”。现在每个 motion 命令都有 cmd_id，nav 必须看到同一个 cmd_id 被接受并完成，才进入下一步。

测试时应该看到什么？
答：发送：
ins reset
nav square 0.6

串口应看到：
[NAV] square drive 1/4 dist=0.600
[NAV] square turn 1/4 yaw_delta=+90.0

2026-07-18 - 连续路径回放 + W25Q 保存/读取怎么用

问：现在 path record 最多能记录多少点？
答：已经提高到 500 点。每个点保存 X、Y、YAW 三个 float，所以 500 点大约占 6000 字节 RAM。新增的约 2KB RAM 来自主栈从 0x1000 降到 0x0800，FreeRTOS heap 仍保持 18KB。

问：现在 path replay 是怎么走的？
答：现在默认是连续路径跟踪，不再按一个个小段停车。回放时 `path_task` 会持续读取 INS 位姿，寻找前视目标点，然后直接输出左右轮 PWM。你之前看到的“停顿明显、折线化”已经改成连续跟踪方式。

问：可以直线和圆弧混合吗？
答：可以。你手推记录的路径可以包含直线、圆弧、S 弯、不规则弧线。`path replay` 不关心它是不是标准圆弧，只会跟踪记录下来的 X/Y/YAW 点列。

问：新加的 W25Q 命令是什么？
答：新增两个核心命令：
path save
path load

也支持两个别名：
path flash save
path flash load

问：path save 做什么？
答：把当前 RAM 里的路径点保存到 W25Q Flash。保存位置从 0x000F0000 开始，使用 2 个 4KB 扇区，共 8KB，不覆盖 INS log 的 0x00100000 区域。

问：path load 做什么？
答：从 W25Q Flash 读取之前保存的路径，并覆盖当前 RAM 里的路径点。读取时会检查 magic、version、点大小、点数量、数据长度和 checksum，防止空 Flash 或坏数据覆盖 RAM。

问：保存一条路径的推荐流程是什么？
答：推荐这样做：
ins reset
path clear
path record start
手推一段直线、圆弧或 S 弯
path record stop
path print
path save

看到类似下面输出就说明保存成功：
[PATH_FLASH] save ok count=... checksum=...

问：断电或清空 RAM 后怎么恢复路径？
答：推荐这样做：
path load
path print

如果 `path print` 打印出的点数和坐标与保存前一致，说明 W25Q 读取正常。

问：读取后怎么回放？
答：把车放回记录起点并对齐方向，然后执行：
ins reset
path replay

注意：`path load` 只恢复路径点，不会自动恢复小车的真实物理位置。回放前还是要把车放回记录起点，并尽量对齐记录时的起始方向。

问：什么时候不能 save/load？
答：正在录制或正在回放时不能保存/读取。需要先执行：
path record stop

或者：
path stop

再执行：
path save
path load

问：如果 path load 报错怎么办？
答：常见情况：
1. `[PATH_FLASH] error: no valid path in flash`：Flash 里还没有保存过有效路径，先录制并 `path save`。
2. `[PATH_FLASH] error: checksum mismatch`：读出的数据校验失败，重新录制并保存。
3. `[PATH_FLASH] error: stop record/replay before load`：当前还在录制或回放，先 `path record stop` 或 `path stop`。

问：完整测试 W25Q 路径保存读取怎么做？
答：最短验证流程：
ins reset
path clear
path record start
手推一小段路径
path record stop
path print
path save
path clear
path print
path load
path print

期望结果：
1. `path clear` 后 `path print` 应该显示 count=0。
2. `path load` 后 `path print` 应该恢复保存前的点数和坐标。
3. 确认恢复正常后，再把车放回起点，执行 `ins reset` 和 `path replay`。

问：本次编译结果？
答：Keil clean rebuild 通过：0 Error(s), 1 Warning(s)。唯一 warning 仍是已有的 LED_PORT 宏重复定义，和 path save/load 无关。

2026-07-18 - 修复长路径 replay 过早点完成

问：为什么 166 个点会在第 32 个点附近停止？
答：不是 Flash 数据丢了。日志里 `replay start count=166` 说明 RAM 里确实有 166 个点。真正原因是旧完成条件只看“当前位置离最后一个点是否小于 0.06m”。长路径、大圆弧、U 形或 S 弯可能在中途就靠近最后点，于是提前判定完成。

问：现在怎么修？
答：现在完成条件改成两个条件同时满足：
1. 离最后一个点小于 0.06m。
2. replay index 已经推进到最后 3 个点以内。

也就是说，如果车中途靠近终点，但还没跟踪到路径尾部，不会停车。

问：我会看到什么新日志？
答：如果中途靠近终点但不允许完成，会看到：
[PATH_TRACK] near final ignored idx=.../... final_dist=... done_idx=...

真正完成时才会看到：
[PATH] replay done track dist=...

问：path status 多了什么？
答：`path status` 现在多了 `final=...`，表示当前位置到最终记录点的距离。这个值可以帮助判断是不是“中途接近终点但不该完成”。

问：怎么测试？
答：用你现在这条 166 点路径：
path load
path print
ins reset
path replay

期望结果：不应该再在 `idx=32/166` 附近停止，应该继续跟踪到接近尾部后才完成。
