小车惯导当前进度（给你看的版本）
更新时间：2026-07-14

问：现在惯导做到哪一步了？
答：已经进入第一版代码实现阶段。现在的目标不是马上自动导航，而是先让小车能持续估计并输出：
1. x_m：从开机位置开始，沿初始前方走了多远。
2. y_m：从开机位置开始，左右偏了多少。
3. yaw_deg：相对开机朝向转了多少度。
4. v_mps：当前线速度。
5. w_dps：当前角速度。

问：第一版用了哪些传感器？
答：用了两个来源：
1. 左右轮编码器：负责计算小车走了多远。
2. IMU 已有 yaw：负责计算小车朝向。
第一版不使用加速度双积分算位置，因为小车上加速度噪声和零偏会让位置很快漂移。

问：M1/M2 怎么定义？
答：当前按你的确认和计划实现：
1. M1 = 左轮。
2. M2 = 右轮。
3. 小车往前走时，左右轮脉冲都按正数处理。
4. 左轮每圈使用 1054 counts/rev。
5. 右轮每圈使用 985 counts/rev。

问：M2 985 每圈会不会影响惯导？
答：不会。关键不是 M2 必须等于 1040，而是程序必须使用实测值。现在第一版已经按 M2=985 换算右轮距离。如果错误使用 1040，右轮距离会被系统性算小或算大，直线和转弯都会偏。

问：代码现在新增了什么？
答：
1. 新增 APP/inc/app_ins.h，定义 INS_Pose_t 和位姿队列。
2. 新增 APP/src/app_ins.c，10ms 运行一次，融合编码器和 IMU yaw。
3. 修改 app_motor_encoder.h/.c，增加左右轮 10ms 增量队列。
4. 修改 app_init.c，创建 INS 队列，并启动 IMU 和 INS 任务。
5. 修改 app_flash.c，取消原来上电擦写 0x00000000 的破坏性 Flash 测试。
6. 修改 Keil .uvprojx，把 app_ins.c 加入编译。
7. 修改 app_tft.c，IMU 检查页面只查看最新 yaw，不再把 IMU 队列数据取走，避免影响 INS。
8. 修改 app_ins.c，INS 上电后立刻开始算位置，Flash 日志延后约 2 秒启动，避免开机等待期间丢编码器数据。

问：串口会看到什么？
答：会周期输出类似：
[INS] X:+0.123 Y:+0.004 YAW:+1.20 V:+0.100 W:+0.50 L:+0.124 R:+0.122 SRC:M F:7

问：Flash 日志现在怎么安排？
答：INS 日志从 0x00100000 开始，预留 8 个 4KB sector，共 32KB。第一版每 200ms 写一条 32 字节记录，用于后续复盘误差。原来的 Flash 测试地址 0x00000000 已避开，不再上电擦写。

问：下一步必须做什么测试？
答：
1. Keil 编译必须 0 error。
2. 静止 10 秒，X/Y/V 应接近 0。
3. 向前推 1 米，X 应接近 1.000，Y 应接近 0。
4. 原地转 90 度，看 yaw 是 +90 还是 -90，并确认是否符合我们定义。
5. 走矩形路线，看回到起点后的 x/y 误差。

问：如果 yaw 方向反了怎么办？
答：只改 APP/src/app_ins.c 里的 INS_IMU_YAW_SIGN，从 +1 改成 -1。不改 IMU 姿态算法本身。

问：如果直线 1 米误差比较大怎么办？
答：优先重新标定轮子：
1. 先确认 M1/M2 左右轮是否接反。
2. 再确认前进时左右轮计数是否都是正。
3. 然后用实测 1m/2m 距离反推左右轮 counts/rev 或轮径修正系数。
4. 最后再考虑更复杂的融合算法。

问：当前最大风险是什么？
答：
1. IMU 任务原来是注释状态，现在已启用，但需要上车确认 yaw 输出稳定。
2. W25Q64、TFT、IMU 可能共享或竞争 SPI 资源，后续如果出现显示/日志冲突，需要加 SPI 互斥。
3. 第一版 Flash 日志是调试格式，还不是最终黑匣子协议。
4. M2 DMA 连续长时间计数还需要实车验证，尤其要确认不会在连续高速计数后停住。

问：为什么我串口只看到 [ATT]，看不到 [INS]？
答：[ATT] 是 IMU 姿态角日志，只能看 roll/pitch/yaw，不能判断小车走了多远。[INS] 才是用来判断误差的位姿日志。如果只看到 [ATT]，说明当前板子上运行的固件里 INS 没有正常输出，常见原因是没有烧录最新固件，或者 FreeRTOS heap 不够导致 ins_task 创建失败。

本次已经修改：
1. [ATT] 打印从每 100ms 降为每 1000ms，避免刷屏。
2. INS 创建失败会打印：[ERR] [INIT] INS task create failed!
3. INS 任务栈从 768 words 降为 512 words。
4. 里程计队列从 32 帧降为 16 帧，降低 heap 压力。
5. 新编译结果：0 Error(s), 1 Warning(s)，Program Size 为 Code=47100, RO-data=6512, RW-data=52, ZI-data=26628。

重新烧录后，判断误差主要看：
[INS] X:+... Y:+... YAW:+... V:+... W:+...

问：INS 应不应该等 IMU 初始化完成后再打印？
答：应该。现在已经改成：INS 任务启动后先等待 IMU yaw 第一帧数据，不再立刻打印 X/Y/YAW。等待期间只会每 1 秒最多提示一次：
[INFO] [INS] Waiting for IMU yaw before pose output

当 IMU yaw 准备好后，会打印：
[INFO] [INS] Ready: yaw zero=... src=...

然后才开始打印真正用于判断误差的：
[INS] X:+... Y:+... YAW:+... V:+... W:+...

等待期间编码器脉冲会被丢弃，不计入起点，避免陀螺仪校准时移动小车污染惯导零点。Flash 日志也会在 INS Ready 后再延后约 2 秒启动。

最新编译结果：0 Error(s), 1 Warning(s)，Program Size 为 Code=47372, RO-data=6608, RW-data=52, ZI-data=26628。
