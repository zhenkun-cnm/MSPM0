MSPM0 路径回放后退差速工程说明
日期: 2026-07-20

一、现在工程里和这个任务有关的文件

1. APP/src/app_path.c
   作用:
   - 负责 path record / path replay。
   - 当前 path replay 使用连续轨迹跟踪。
   - 已经能记录路径点、选择前视点、计算航向误差、输出左右轮 PWM。
   - 目前已经有 dir=F / dir=B 的方向识别日志。

   当前问题:
   - 后退段已经能识别为 dir=B。
   - 但是后退控制仍主要依赖“全局反向 + 左右正 PWM”。
   - 这种方式能简单后退，但后退差速拐弯能力不够。

2. APP/src/app_tb6612.c
   作用:
   - 负责接收电机命令队列，并控制 TB6612。
   - 已经支持左右轮独立 signed PWM:
     MOTOR_CMD_LEFT_SIGNED_SPEED
     MOTOR_CMD_RIGHT_SIGNED_SPEED

   重要结论:
   - signed PWM 为正时，该轮前进。
   - signed PWM 为负时，该轮后退。
   - 这是实现后退差速拐弯的正确底层接口。

3. APP/inc/app_tb6612.h
   作用:
   - 定义电机命令类型。
   - 已包含 signed speed 命令，不需要新增命令类型。

4. board/empty/port/src/port_tb6612.c
   作用:
   - 真正操作 TB6612 方向 GPIO 和 PWM。
   - 已经有左右轮独立方向设置函数。

5. APP/src/app_tft.c
   作用:
   - TFT 菜单。
   - 后续需要增加 PID -> PathTrack 页面，用来调 PathTrack Kp/Ki/Kd。

6. task_plan.md

7. findings.md

二、现在的任务是什么

当前任务:
让 path replay 在后退路径中也能差速拐弯。

更具体地说:
- 用户手动向后推车，并且后退过程中带弯。
- path record 记录这条轨迹。
- path replay 回放时，车应该保持车头方向，不先转 180 度。
- 车应该倒着沿轨迹走，并能通过左右轮不同速度完成后退拐弯。

现在已经做到:
- INS 可以记录后退位移。
- path replay 可以识别 dir=B。
- 车可以单纯后退。

现在还没做到:
- 后退时稳定地差速拐弯。
- 参数可以方便调整。

需要整理的参数:

- BaseFwdPWM: 前进基础 PWM。
- BaseBackPWM: 后退基础 PWM。

- DoneDist: 终点距离阈值。

阶段 5: 后退段 signed PWM
状态: 未完成

目标:
只在后退段使用左右轮 signed PWM，尽量不影响前进段。

保守策略:
- 前进段保持当前已有输出方式。
- 后退段改为:
  左轮发送 MOTOR_CMD_LEFT_SIGNED_SPEED
  右轮发送 MOTOR_CMD_RIGHT_SIGNED_SPEED

后退直线示例:
- left_pwm = -16
- right_pwm = -16

后退左/右转示例:
- left_pwm = -22
- right_pwm = -8
或:
- left_pwm = -8
- right_pwm = -22

注意:
先允许内侧轮降到 0。
暂时不默认让一侧前进一侧后退，避免动作太激烈。

四、如何验证是否成功

测试 1: 前进段不受影响

操作:
ins reset
path clear
path record start
向前推一段直线或小弯
path record stop
path print
把车放回起点
ins reset
path replay

成功现象:
- 串口出现 dir=F。
- 车辆按原来的前进回放方式走。
- 没有明显比之前更差。


测试 2: 后退直线

操作:
ins reset
path clear
path record start
保持车头不转，向后推一段直线
path record stop
path print
把车放回起点
ins reset
path replay

成功现象:
- 串口出现 dir=B。
- 后退 signed PWM 阶段完成后，日志应看到负 PWM，例如:
  pwm=-16/-16
- 车辆后退，不先转 180 度。


测试 3: 后退弯曲

操作:
ins reset
path clear
path record start
保持车头方向，向后推并带弯
path record stop
path print
把车放回起点
ins reset
path replay

成功现象:
- 串口出现 dir=B。
- PWM 是负数，并且左右不相等，例如:
  pwm=-22/-8
  pwm=-8/-22
- 车辆倒车时能拐弯，而不是只能直退。


测试 4: 混合轨迹

操作:
记录一段先前进、再后退的轨迹。

成功现象:
- 前进段日志 dir=F。
- 后退段日志 dir=B。
- 前进段不明显退化。
- 后退段可以拐弯。
- 方向切换时没有明显抽动、乱转或提前结束。


五、判断失败时怎么看

情况 A: 一直是 dir=F
说明:
- path replay 没识别出后退段。
可能原因:
- 记录点 yaw 不稳定。
- 路径点之间位移太小。
- 车被推的时候车头方向和移动方向夹角没有超过 90 度。

情况 B: dir=B 但车还是前进
说明:
- signed PWM 或 TB6612 单轮方向映射需要检查。
下一步:
- 用 speedtest 或单轮 signed speed 做台架测试。

情况 C: dir=B 且车后退，但不会拐弯
说明:
- 后退差速控制参数不够。
优先调整:
- TrimMax 增大。
- BaseBackPWM 适当提高。
- Lookahead 减小。
 - PathTrack Kp 增大。

七、2026-07-21 诊断代码状态

结论更新:
- 双驱动轮加万向轮底盘的前进和后退共用同一组 PathTrack 参数。
- 现有后退段已经使用“全局反向 + 左右不同 PWM”。因此只把同一对幅值改成负 signed PWM，不会自动增加差速转弯能力。
- signed PWM 仅作为执行层对照测试，不在本次接入 path replay。

2026-07-21 首次台架结果和崩溃修复:
- `speedtest reverse 20 12` 已测得左/右实际速度 `-166/-135 mm/s`，证明现有全局反向加不同 PWM 已能形成倒车差速。
- 第二条长日志打印时发生 M0+ HardFault（PC=0）。诊断为 `ins_cmd` 任务的 160 words 栈空间不足：该任务保留 UART 行缓冲并调用含 128-byte 格式化缓冲的日志函数，且原来未启用 FreeRTOS 栈溢出检测。
- `INS_CMD_TASK_STACK_WORDS` 已提升为 256 words；`speedtest status` 新增 `stack_min_free=<words>`，用于确认高水位余量。
- 本次不修改 PathTrack 参数、path replay 或 TB6612 控制律。

已完成（代码和 Keil 构建验证）:
- 保持全部 PATH_TRACK 参数和 path replay 的普通 PWM 输出流程不变。
- 新增 `speedtest reverse <left_pwm> <right_pwm>`，复现 path replay 当前的全局反向差速输出。
- 新增 `speedtest signed <left_pwm> <right_pwm>`，用于比较独立 signed PWM 的实际轮速结果。
- `[PATH_TRACK]` 现在输出路径段、记录 yaw、移动方向、段方向误差、跟踪角、原始/限幅 Trim、原始/最终左右 PWM。
- 前进/后退判定切换时会输出 `[PATH_DIR]` 日志。

现场测试顺序（先将驱动轮架空）:
1. `speedtest reverse 20 12`，保存至少 2 秒日志。
2. `speedtest reverse 12 20`，确认左右实际负速度差随请求交换。
3. `speedtest signed -20 -12` 和 `speedtest signed -12 -20`，与前两项比较。
4. 录制前进后退混合路径，按原有 `path record start` / `path replay` 流程检查 `[PATH_TRACK]` 与 `[PATH_DIR]`。

结果判定:
- 若全局反向已经产生正确的左右负速度差，signed PWM 不应加入 path replay；后续只根据路径日志修正控制律或前视/方向判定。
- 若全局反向的请求 PWM 不同但实际轮速没有差异，优先检查 TB6612、机械死区或编码器数据。
- 若 signed PWM 与全局反向的实际结果不同，再决定是否在路径回放中采用 signed PWM。

情况 D: 后退拐弯太猛或抖动
说明:
- 控制太激进。
优先调整:
- PathTrack Kp 降低。
- TrimMax 降低。
- Slew 降低。
- Lookahead 增大。


2026-07-21 UART log non-blocking update
- The dynamic FreeRTOS queue/log_tx fallback caused an immediate boot HardFault: PendSV read pxCurrentTCB=0x07070707, an initial task-stack fill value. It is removed.
- Normal logs now use UART0 TX interrupt with two static 128-byte records: one active record and one newest pending record. Tasks only copy data under a short critical section and never wait for UART.
- A new record can replace only the unsent pending record and increments log_overwrite; active output is never overwritten or interleaved. RX buffer is 128 bytes for the existing 80-byte command line.
- Stack-overflow level 2 and malloc-failed hooks now report direct UART fault text and reset. Path replay and motor control are unchanged.

2026-07-21 UART async logging rollback
- User chose stability after repeatable boot-time faults. All queue/task and TX-interrupt log changes are removed.
- UART is restored to original direct blocking output, RX buffer is restored to 256 bytes, and extra FreeRTOS fault hooks are disabled.
- Reverse speedtest diagnostics, shared path parameters, and motor control remain unchanged.
- Target verification: run reverse 20/12 and 12/20 for five seconds; require complete records, no HardFault, positive stack_min_free, and log_overwrite=0.
